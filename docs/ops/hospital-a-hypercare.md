## 1. 目标与验收口径

- 目的：医院 A 上线（E23-T11 切换完成）后的两周观察期内，医院用户与监控发现的问题**在分级时限内得到响应**，异常早发现早处置，观察期结束时平稳移交常态支持。

  1. **时限表在册**：§3 分级与响应时限表与工具常量一致（防漂移校验锁定，§10）；
  2. **台账可判**：观察期问题台账（§5，GitHub Issues + CSV 导出）经 `scripts/hypercare_verify.py --ledger` 判定**全部按时响应**（每条 responded_at − reported_at ≤ 分级时限；未响应的截至判定时刻未超时）；
  3. **巡检在册**：§6 每日巡检（机器侧六项 + 人工清单）执行且留痕，异常项全部进入台账闭环。

## 3. 问题分级与响应时限（SLA 表）

> 分级梯子与渗透（OQ-112）、UAT（OQ-122②）共用同一套 GitHub label，不另立体系；「响应」= **受理登记 + 首个实质动作**（分诊结论 / 缓解措施 / 修复 PR 任一，`response_action` 留痕），不是「已读」。

| 级别 | label | 定义 | 响应时限（机器判定） | 处置时限（人工闭环） |
|---|---|---|---|---|
| P0 阻断 | `severity:high` | 医院端或平台端全站不可用；数据损坏 / 丢失风险；安全事件（越权访问迹象、批量泄露） | **15 分钟**（7×24） | 4 小时内恢复服务或按 go-live §7 中止回切 |
| P1 严重 | `severity:medium` | 核心链路不可用且无绕行：登录、患者登记、基线、随访录入、任务流转、通知 | **30 分钟**（7×24） | 1 个工作日内修复或稳定绕行 |
| P2 一般 | `severity:low` | 有绕行的功能缺陷；性能明显劣化（核心页面 > 5 秒）；非核心功能错误 | **120 分钟**（工作时间） | 3 个工作日内 |
| P3 建议 | `severity:info` | 文案、易用性、优化建议 | **480 分钟**（1 个工作日） | 排期处理（进常态需求池） |

- **机器判定口径（从严）**：`hypercare_verify.py` 按自然时钟分钟数判定（P3 的「1 个工作日」以 8 小时 = 480 分钟从严），不做工作时间换算；夜间 / 假期接报的 P2/P3 如按工作时间口径顺延，triage 在 Issue 评论留痕说明，机器口径不改；
- 判定命令与输出见 §5；任一条 FAIL 即验收句未达成，按 §4 升级。

## 4. 处置流程（接报 → 关闭）

1. **受理登记**（接报后 15 分钟内）：任何通道的发现当场建 GitHub Issue（本仓库，label `HYPERCARE` + `E23` + 分级 label；缺陷类再加 `bug`），正文首行写幂等编号 `HYPC-W{周}-{序}`（如 `HYPC-W36-01`，与 UAT-ID / PENTEST-ID 同梯子，OQ-122①）；
2. **分级复核**：接报人初判分级；16:00 triage（与 UAT 口径一致）复核——误报 / 重复合并的结论留 Issue 评论，不改编号；
3. **定责**：按 §5 分担面标注 owner（全栈 1 / 全栈 2 / 运维 / 产品 / 测试 / 医院）；跨面问题定主责 + 协办；**P0 不分面**（谁先接谁牵头，恢复后再移交）；
4. **处置**（三选一，同 `docs/testing/uat-remediation-hospital-a-fullstack1.md` §3 口径）：
   - **修复**：一类缺陷一个分支 / PR，提交说明 `fix({scope}): E23-T13 {HYPC-编号} {标题}`，PR 关联 Issue；**TDD——先写失败测试锁定行为再修**（AGENTS §8）；
   - **缓解**：暂未根治但有等效控制（配置 / 开关 / 流程绕行），控制点与残余风险留 Issue，跟踪项进 OQ 或 P3；
   - **延期**：修复代价大于影响，医院方书面接受后随遗留项清单留痕（观察期退出评审输入）；
   - 处置涉及生产动作（回切、租户停用、单院恢复）一律走对应 runbook（§7），不在 Issue 里口头约定；
5. **验证**：修复版本过 CI + 冒烟（E23-T12 A 组口径）后发生产窗口；P0/P1 必须由报告方或测试复测通过；
6. **关闭**：台账行置 RESOLVED（`resolved_at` 留痕）；超时未响应 / 超时未处置按 §2 升级。

## 5. 问题台账与分担面

### 5.1 台账（GitHub Issues → CSV）

- 工作清单唯一事实源 = GitHub Issues（OQ-122①暂行：若采购独立缺陷系统，只换导出适配层，列与 HYPC- 编号不变）；
- 机器判定用 CSV 导出（模板 `docs/ops/hypercare-findings-template.csv`，13 列，表头与脚本 `LEDGER_COLUMNS` 逐字一致）：
  `finding_id`（HYPC- 编号）、`reported_at`（接报时刻，YYYY-MM-DD HH:MM）、`channel`（值班电话 / 医院服务群 / 巡检 / 监控告警 / 邮件）、`severity`（P0~P3）、`module`（模块标识）、`summary`（脱敏摘要，**疑似真实手机号 / 身份证号一律拦截**）、`triaged_at`、`owner`（全栈1 / 全栈2 / 运维 / 产品 / 测试 / 医院）、`responded_at`、`response_action`（响应 = 受理 + 首个实质动作）、`resolved_at`、`status`（OPEN / RESPONDED / RESOLVED）、`issue_url`；
- 判定（观察期每日 18:00 与退出评审各一次）：

```bash
python3 scripts/hypercare_verify.py --ledger <台账.csv> [--asof "YYYY-MM-DD HH:MM"]
```

  全部 `[PASS]` 才算「按时响应」达成；`[FAIL]`（超时响应 / 超时未响应）逐条按 §2 升级、§4 处置。

## 6. 观察期每日巡检（值班人执行，09:00 与 17:00 各一轮）

### 6.1 机器侧（只读 SQL，`scripts/hypercare_verify.py` 巡检口径）

生产执行（持账号运维或值班人经跳板机，**只读账号**，口令只经环境变量 `CRDP_HYPERCARE_MYSQL_PASSWORD` 进 mysql 客户端进程环境，不进 argv、不落盘）：

```bash
export CRDP_HYPERCARE_MYSQL_PASSWORD='<只读账号口令>'
python3 scripts/hypercare_verify.py --host <生产 RDS 地址> --port 3306 \
  --db t_<租户编码> --user <只读账号>
```

| 检查项 | 口径（阈值） | 异常去向 |
|---|---|---|
| HC-D1 登录失败激增 | `aud_login_log` 24 小时失败 > 10 次 | 安全事件线索 → §7 安全行 + §3 P0 分级研判（E08-T05 告警同源） |
| HC-D2 调度作业失败 | `job_tenant_run` 当日与昨日非 SUCCESS > 0 条 | 按 `error_text` 排查并补跑（补跑幂等，技术方案 §15） |
| HC-D3 outbox 分发积压 | `sys_outbox` PENDING > 1 小时 > 0 条 | 查分发作业（E09）；组织变更事件不丢（PLT-ORG-013） |
| HC-D4 通知发送失败 | `ntf_send_log` 24 小时 FAILED > 0 条 | 按 `detail` 排查短信 / 站内通道（A-NTF-006） |
| HC-D5 导入作业卡死 / 部分失败 | `imp_job` UPLOADED/PRECHECKING 卡死 > 24 小时或 PARTIAL_FAILED > 0 个 | `docs/ops/hospital-a-import-rollback.md` §1 决策树 + go-live §7 |
| HC-D6 任务逾期占比 | `fu_task` OVERDUE 占比 > 20% | 查每日调度链（`FollowupTaskScheduler`）与提醒是否到位（A-FU-026） |

- 任何一项 FAIL：当场建 Issue 进台账（§4），按 §3 分级（多数为 P1/P2）；
- 本地 / CI 自验：`--drill` 在克隆真实 Flyway schema 的隔离库（`t_hypcdr`，LIKE `t_demoa` 建表、结束整库删除，不碰共享演示数据）上跑「空库基线六项全 PASS → 注入六类异常逐项检出 → 清场归零」（§10）。

## 10. 自动化对照（CI 恒跑）

`scripts/hypercare_verify.py` 在 CI 与本机按三种模式运行（`.github/workflows/ci.yml`）：

```bash
python3 scripts/hypercare_verify.py --selftest   # 纯逻辑自检：时限表 / SLA 判定 / 台账校验 / 只读护栏
python3 scripts/hypercare_verify.py              # 本手册防漂移校验（时限表 / 台账列 / 巡检项 / 互引 / 接线）
python3 scripts/hypercare_verify.py --drill      # compose MySQL：隔离库基线全 PASS + 六类异常逐项检出 + 清场归零
```

- 防漂移校验锁定：验收原句与依赖、时限表数字与脚本常量逐字一致、台账 13 列与 `LEDGER_COLUMNS` 一致（模板表头同查）、巡检项 HC-D1~D6 与阈值在册、go-live §6/§7 承接、互引文档存在、ci.yml 接线、`docs/README.md` 索引；
- `--ledger`（现场判定）与 `--host`（生产巡检）不在 CI 运行，由值班人 / 持账号运维按 §5 / §6 执行。
