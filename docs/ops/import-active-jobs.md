# 导入活动作业约束上线与冲突处置（OQR-03）

关联 E18-T02 / E18-T05、OQ-101④；迁移 `V140__imp_job_active_slot.sql`。本手册只规定检查与处置流程，不代表生产已经迁移或异常恢复已经验收。

## 上线前检查

1. 安排维护窗口，暂停新增导入请求、确认与重试入口，等待已有执行结束；核实所有应用副本、线程池与在途任务，避免迁移期间旧版本应用继续写入。
2. 使用受控数据库连接，逐个已开通随访模块、含 `imp_job` 表且需要升级的租户库运行 [只读检查 SQL](../../deploy/checks/import-active-jobs.sql)。清单只包含作业 ID、状态、操作人 ID 与时间，不导出原始文件名或患者内容。平台库不执行本迁移。
3. `active_jobs <= 1` 才可升级；有一条真实运行中作业时优先等待其完成。多条活动作业时保持阻断，记录作业 ID、执行副本、批次进度、实际写入与责任人。
4. 迁移账号须有建表 / 改表、索引及 `CREATE TEMPORARY TABLES` 权限；临时表只用于迁移连接，运行期导入不需要新增数据库权限。按正常发布流程运行 Flyway。迁移先通过临时校验表检查活动行数，多活动时报 `ck_imp_job_resolve_active_conflicts` 并停止；最终唯一索引仍会拦截预检之后出现的竞争。它不会自动选赢家、删除作业或改状态。
5. 确认生成列 `active_slot` 与唯一索引 `uk_imp_job_active_slot` 已存在，再恢复应用流量。按测试清单验证并发竞争返回 40901、终态释放及不同租户独立运行。

迁移无新增持久业务表，不修改旧迁移。MySQL DDL 非事务回滚，发布重试前检查 Flyway 历史和实际表结构，按既有迁移失败处理流程修复；不能在未核实结构时直接忽略错误或改历史校验和。

## 存量冲突与异常恢复

- 对仍在执行的 PRECHECKING / IMPORTING 作业，等待其正常结束；不能强行把状态改为终态释放活动槽。
- 对未执行的 UPLOADED 作业，核实未派发 / 未启动后，通过现有取消接口放弃并保留审计。取消与启动预检并发时由 CAS 决定，取消失败后重新核实执行状态。
- PRECHECKING / IMPORTING 即使长时间无更新时间，也不能仅凭超时判断已停止。确认全部副本停止执行、事务结束后，先核对已完成批次和写入，使用经验证的恢复流程继续原作业。
- 当前整改不新增自动超时解锁、接管作业或手工状态更新入口。若没有可用且已验证的恢复入口，继续保持阻断，提交作业与批次证据制定恢复方案；不得执行裸 UPDATE / DELETE、重建作业或重跑已提交批次来绕过唯一约束。
- 每次处置记录环境、租户、作业 ID、核实证据、执行人、操作原因及结果，敏感文件保持原受控存储，不进入仓库或日志。确认冲突消除后重新执行只读检查，再重试迁移。

## 状态与槽位

| 状态 | active_slot | 行为 |
|---|---|---|
| UPLOADED / PRECHECKING / IMPORTING | 1 | 同院只能有一行；创建、确认、重试均受同一约束 |
| PRECHECKED / PRECHECK_FAILED / PARTIAL_FAILED | NULL | 不占槽；确认与重试须重新争用，冲突保持原状态 |
| DONE / CANCELLED / ROLLED_BACK 等终态 | NULL | 状态写入时原子释放，无独立解锁步骤 |

确认提交在同一事务内保存选项 / 范围、切批并争用槽，失败全部回滚。重试先在请求线程完成 CAS 争用再派发执行，失败同步返回 40901；不会先返回“已受理”再由后台吞掉竞争异常。此约束按租户数据库生效，不在表内添加 tenant_id。
