## 1. 目标与口径

- 目的：医院 A 用户（科主任 / 病区医生 / 随访员 / 数据录入员，角色模板见 A 规格 §10）在 UAT 级环境按 §5 脚本验收本院业务全范围，发现问题进缺陷库修复关闭，最终在 §8 签字单上书面确认，作为 A 上线的放行条件。
- 验收口径拆解（「UAT 签字确认」四要素，缺一不算达成）：
  1. **执行**：医院用户按 §5 脚本逐条执行并记录（P0/P1 用例执行率 100%，§7）；
  2. **入库**：UAT 发现 100% 进入缺陷库（GitHub Issues，§6，口径见 OQ-122）；
  3. **判据**：§7 签字判据全部满足（阻断 / 严重清零等）；
  4. **签字**：医院方 UAT 负责人与我方产品在 §8 签字单上签署结论（通过 / 有条件通过）。
- 缺陷库载体：本仓库 GitHub Issues（沿用 OQ-112 ① 暂行口径，UAT 侧细则见 OQ-122；若产品后续采购独立缺陷系统，只换 `uat_intake.py` 的适配层，CSV 列与 UAT-ID 口径不变）。

节奏（W34–W35 执行期每个工作日）：晨会 15 分钟（昨日进展 / 今日计划 / 阻塞）→ 白天执行与记录 → 16:00 缺陷 triage（定级复核、定责、阻断当日响应）→ 日报（执行数、新发现、阻塞，产品发医院方 UAT 负责人）。

分级与时限（宣讲内容，口径见 §6）：

| 级别 | 定义 | 入库时限 | 响应时限 |
|---|---|---|---|
| 阻断 | 主流程 / 主功能不可用，或数据错误（对应 label `severity:high`） | 当日 | 当日给出修复或绕行结论 |
| 严重 | 主要功能错误但有绕行（`severity:medium`） | 24 小时 | triage 定责后 1 个工作日内修复计划 |
| 一般 | 次要功能 / 体验问题（`severity:low`） | 48 小时 | 排期处理 |
| 建议 | 优化建议，不阻塞验收（`severity:info`） | 48 小时 | 记录跟踪，上线后再评 |

## 5. UAT 脚本（医院用户照此执行）

> 用法：执行人按「角色」列用自己的 UAT 账号；每条用例在执行记录表记「通过 / 不通过 / 阻塞」+ 证据（截图编号，存 UAT 共享目录不入仓库）；不通过的按 §6 当日整理入库。脚本里的菜单 / 路由与当前实现一致（菜单树：首页 `/dashboard`、我的任务 `/followup/task`、随访 → 患者档案 / 随访计划 / 报告单与资料 / 统计、系统管理各页；页面规格见 `docs/design/pages.md` 对应小节），核心链路本机预演记录见 §10。
> 级别：**P0** 主流程（签字判据要求 100% 执行）、**P1** 重要功能、**P2** 次要 / 体验。共 47 条（P0 21 / P1 20 / P2 6）。

## 6. 问题跟踪（机制交付 · 本任务仓库侧完成）

流程：现场记录（UAT 执行记录表：用例编号 / 结果 / 证据截图编号，截图存 UAT 共享目录**不入仓库**）→ 当日整理为 CSV（列定义即 `docs/testing/uat-findings-template.csv` 表头，模板行是虚构示例，**真实发现只放本地文件，不提交仓库**——AGENTS §5.5）→ `scripts/uat_intake.py` 校验并建 Issue。

```bash
# 校验 + 预览（默认 dry-run，不联网）
python3 scripts/uat_intake.py path/to/uat-w34.csv
# 真正入库（token 取自 git credential fill；幂等：UAT-ID 已存在则跳过）
python3 scripts/uat_intake.py path/to/uat-w34.csv --apply --ensure-labels
# 工具自检（CI 恒跑，不联网）
python3 scripts/uat_intake.py --selftest
```

- 列与校验：12 列（finding_id、title、severity、module、page_or_api、reporter_role、description、reproduce_steps、expected_behavior、actual_behavior、evidence_ref、fix_suggestion）；空值、非法分级、非法模块、重复编号、疑似真实手机号 / 身份证号一律拦截；
- 编号口径：`UAT-W{周次}-{流水}`（如 UAT-W34-001，W33/W34/W35 对应发现所在周）；
- 分级映射（OQ-122 ②）：阻断 / 严重 / 一般 / 建议 → label `severity:high / medium / low / info`（梯子与渗透共用，OQ-112），另打 `bug`、`UAT`、`E23`；
- 修复 / 复测路由：Issue 正文标注修复任务 E23-T09 / E23-T10（每日 16:00 triage 定责到人）与复测任务 E19-T10；复测通过后关闭并在 Issue 留复测结论；
- 时限：见 §2 分级表；阻断当日入库当日响应，修复版本进 UAT 前先过 CI + A 组冒烟（§3 版本冻结）；
- 闭环口径：「阻断 / 严重清零」以 label `UAT` 的 Issue 全量状态为证（M3 出口与 §7 判据的数据来源）；
- 真实数据红线：发现描述不得含真实患者标识（工具自动拦截）；证据只引记录表行号 / 截图编号；UAT 环境本身不录真实患者（§3）。

## 7. 签字判据（Definition of UAT Pass）

全部满足才可进入 §8 签字：

1. **覆盖**：P0/P1 用例执行率 100%；P2 执行率 ≥ 80%（未执行项逐条说明原因并经医院方 UAT 负责人确认）；
2. **缺陷**：阻断（severity:high）与严重（severity:medium）全部关闭＝修复 + 复测通过；一般（severity:low）全部有处置结论（关闭，或医院书面接受的延期上线处理）；建议（severity:info）全部入库跟踪；
3. **数据**：J-2 抽样核对与汇总数核对一致（E23-T06 验收联动，导入演练记录为证）；
4. **遗留**：遗留项书面清单（问题、影响、处置、责任人、期限）经双方确认，作为签字单附件；
5. **结论三档**：**通过** / **有条件通过**（遗留项不阻塞上线且有书面处置与期限）/ **不通过**（判据 1–3 任一不满足：修复后 W35 内复走一轮；仍不通过 → A 上线决策升级，产品 + 医院书面决定是否顺延 W36）。

判据数据来源：label `UAT` 的 Issue 列表（状态汇总）+ 执行记录表统计（按用例编号）。
