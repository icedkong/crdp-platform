## 1. 目标与口径

- 目的：医院 C 用户（科主任 / 医生 / 随访员 / 护士 / 病案室资料录入员，角色模板见 C 规格 §10）在 UAT 级环境按 §5 脚本验收本院业务全范围（植入与程控随访、纸质资料电子化与补录），发现问题进缺陷库修复关闭，最终在 §8 签字单上书面确认，作为 C 上线的放行条件。
- 验收口径拆解（「UAT 签字确认」四要素，缺一不算达成，与 A 手册 §1 同构）：
  1. **执行**：医院用户按 §5 脚本逐条执行并记录（P0/P1 用例执行率 100%，§7）；
  2. **入库**：UAT 发现 100% 进入缺陷库（GitHub Issues，§6，口径见 OQ-122 ①② / OQ-153 ①）；
  3. **判据**：§7 签字判据全部满足（阻断 / 严重清零等）；
  4. **签字**：医院方 UAT 负责人与我方产品在 §8 签字单上签署结论（通过 / 有条件通过）。
- 缺陷库载体：本仓库 GitHub Issues（沿用 OQ-112 ① / OQ-122 ① 暂行口径，C 侧细则见 OQ-153；若产品后续采购独立缺陷系统，只换 `uat_intake.py` 的适配层，CSV 列与 UAT-ID 口径不变）。
- 与 A UAT（E23-T08）的差异：① 数据面无 A 式脱敏样本链路（E23-T05），改为 **V137 预置 + E23-T27 导入演练批次 + UAT 现场虚构造数**（§3，OQ-153 ②）；② **H5 手机拍照上传在 C 的 UAT 范围内**（A 手册明确排除，C 为 P1 交付功能，§5 M-3）；③ 已知口径差异 **OQ-148**（补录记录不自动完成窗口内任务，替代路径见 §5 I-2）须在 UAT 向医院披露并取得书面确认，列入 §7 遗留判据；④ E21-T31 评审移交的 **UAT 复核清单 5 项**（§5 末表）随 UAT 请医院逐项确认。

## 5. UAT 脚本（医院用户照此执行）

> 用法：执行人按「角色」列用自己的 UAT 账号；每条用例在执行记录表记「通过 / 不通过 / 阻塞」+ 证据（截图编号，存 UAT 共享目录不入仓库）；不通过的按 §6 当日整理入库。脚本里的菜单 / 路由与当前实现一致（菜单树：首页 `/dashboard`、我的任务 `/followup/task`、随访 → 患者档案 / 随访计划 / 报告单与资料 / 统计、系统管理各页；C 专属入口：患者档案内植入记录与参数趋势页签、远程监测入口、待归档区），页面规格见 `docs/design/pages.md` 对应小节；核心链路本机预演记录见 §10.1。
> 级别：**P0** 主流程（签字判据要求 100% 执行）、**P1** 重要功能、**P2** 次要 / 体验。共 65 条（P0 36 / P1 26 / P2 3）。
> 用例与评审用例集（C-ACC-01…45）的对应关系在「预期（依据）」列标注；机器面已覆盖的行为（各验收 IT / 单测）UAT 仍须医院用户按本院口径走一遍——UAT 验的是「医院用户认可」，不是「代码能跑」。

## 7. 签字判据（Definition of UAT Pass）

全部满足才可进入 §8 签字：

1. **覆盖**：P0/P1 用例执行率 100%；P2 执行率 ≥ 80%（未执行项逐条说明原因并经医院方 UAT 负责人确认）；
2. **缺陷**：阻断（severity:high）与严重（severity:medium）全部关闭＝修复 + 复测通过；一般（severity:low）全部有处置结论（关闭，或医院书面接受的延期上线处理）；建议（severity:info）全部入库跟踪；
3. **数据**：K-1 / K-2 建档与扫描件关联三口径核对一致（E23-T27 验收联动，演练记录为证）；
4. **遗留**：遗留项书面清单（问题、影响、处置、责任人、期限）经双方确认，作为签字单附件；**须包含 OQ-148 口径差异的医院确认结论与 §5 UAT 复核清单 5 项的确认结果**（尤其附录 A 字段范围 / 必填的逐项确认记录）；
5. **结论三档**：**通过** / **有条件通过**（遗留项不阻塞上线且有书面处置与期限）/ **不通过**（判据 1–3 任一不满足：修复后 W45 内复走一轮；仍不通过 → C 上线决策升级，产品 + 医院书面决定是否顺延 W46，注意 W46 为国庆前最后一周）。

判据数据来源：label `UAT` 的 Issue 列表（按 UAT-ID 周次 W44 / W45 过滤 C 侧）+ 执行记录表统计（按用例编号）。
